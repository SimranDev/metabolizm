# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

## Product

**Metabolizm** is a Health & Fitness app (iOS + Android) — a "swiss-knife for fitness" whose **core is weight, calorie, and macro/micro tracking**, with many surrounding features. Users create a profile, set goals (gain muscle / lose weight / maintain, with BMR·TDEE-based targets), log food by search or **barcode scan**, get **recipe** suggestions, view a **health dashboard**, and import **steps/activity** from other fitness apps.

Intended stack for feature work:
- **Backend:** cloud from the start — auth + hosted database + multi-device sync.
- **Activity/steps:** Apple Health (iOS) + Android **Health Connect**.
- **Food data / barcodes:** **Open Food Facts + USDA** FoodData Central.
- **Monetization:** subscription tiers (free / pro / pro max) — the header's plan icon reflects the tier.

## Priorities & constraints

**Performance and small app size come first — ahead of animations and heavy assets.** Prefer lightweight dependencies and native primitives (SF Symbols on iOS, Material `md` symbols on Android) over large bundled images or Lottie; lazy-load where sensible and watch bundle/app size as features land.

Hard, not the usual soft delete: a `deleted_at` row still holds the FK. `diary_entries.food_id` and `user_targets.set_by` are `SET NULL`, so another member's logged history and a coach-set target survive the setter's departure. ## Groups — the masking invariant

Social accountability: private, invite-only groups (`partner` | `family` | `friends` | `trainer`, ≤ ~50 people) whose members share nutrition data with each other. No public discovery, no follower graph, and deliberately **no feed table** — feeds are computed at read time (fan-out-on-read).

Each membership carries its own `share_config` (`calories`, `macros`, `mealNames`, `mealDetail`, `weightTrend`, `streaks`, plus `adherenceOnly`); the category picks the defaults at join time ([CATEGORY_SHARE_DEFAULTS](packages/shared/src/groups-schemas.ts)) and the member can edit them per group at any time.

**Non-negotiable, and the reason [groups/masking.ts](apps/api/src/groups/masking.ts) and its regression suite ([masking.test.ts](apps/api/src/groups/masking.test.ts), `pnpm test`) exist:** all masking happens server-side in the service layer before serialization. Payloads are built **allowlist-style** — a field is *added* only when the subject's config exposes it, never copied wholesale and stripped — so an unshared field is **absent from the JSON, not null**, including in nested/joined data. Anything new that reads another member's data goes through `masking.ts`; never serialize a `daily_summaries` or `diary_entries` row into a group response directly.

Rules that fall out of that:
- `adherenceOnly` returns server-computed booleans (`proteinHit`, `caloriesInRange`, `logged`) — absolute kcal/gram/weight numbers never leave the API for that member.
- Masking reads the member's **current** config at read time, so a change takes effect immediately for all past and future days. There are no consent snapshots.
- `status` `left`/`removed` excludes that member from every group read (loads are scoped to `active` members, so their rows never enter a query).
- Leaderboards rank by adherence % and logging streak only — **never** by raw calories or weight, which aren't in the response at all.
- Share-config *updates* are partial patches ([groupSharePatchSchema](packages/shared/src/groups-schemas.ts)) with no per-field defaults. A schema with `.default(false)` per field would materialize every unmentioned toggle as `false` and silently switch off what the caller didn't name; `groupShareConfigSchema` (all-false defaults) is only for normalizing what's *stored*, where a missing key must read as off.

**On the mobile side** ([src/components/groups/](apps/mobile/src/components/groups/), the `groups` tab and the root-stack drill-downs), that absence is what drives the UI: a field being `undefined` means *private*, never *zero*. Every slot a shared value could occupy renders either the value or a designed locked chip ([not-shared.tsx](apps/mobile/src/components/groups/not-shared.tsx)) — **never a blank**, which would read as "didn't log". Nothing substitutes a default for a withheld field. Share-config edits go through [shareConfigDiff](apps/mobile/src/lib/groups/index.ts) so only changed keys are sent. Leaderboard and roster copy always pairs the percentage with "logged n of m days", because unlogged past days score zero while the current week's remaining days are excluded — a bare percentage would read as judgement rather than a count.

`daily_summaries` is the read model behind all of this: one row per (user, local day), recomputed by [SummariesService](apps/api/src/summaries/summaries.service.ts) inside the same transaction as every diary write, snapshotting the `user_targets` row effective **for that day** — which is what stops a mid-week target change from rewriting past adherence. "Today" in a group read is each member's own local date per their `users.timezone`, never one global date.

That row has **two writers, and they must stay disjoint**: `recomputeDay` owns every nutrition column and never touches `weight_kg`; `recomputeDayWeight` owns `weight_kg` and never touches nutrition. They share a primary key, so merging their `ON CONFLICT ... SET` maps into one "tidier" upsert makes each writer clobber the other's column with a stale value ([writers.test.ts](apps/api/src/summaries/writers.test.ts) exists to catch that). The weight path deliberately snapshots **no targets** — a day with only a weigh-in must stay unscorable, or logging your weight would register as a 0 kcal adherence miss.

## Group invitations

Two ways into a group, one table. `group_invites.kind` (`link | direct`) is the discriminator, **stored rather than derived** from `invited_user_id IS NOT NULL` — a nullable column standing in for a three-mode union is where derivation stops paying (unlike `isVerified` from `review_status`, which is total). Two CHECK constraints hold the modes apart in the database rather than in memory.

- **A `direct` invitation's token never leaves the server.** `acceptInvite` authenticates the caller but compares them to nothing, and `previewInvite` is public — so returning the token would make a person-targeted invitation a forwardable credential, and whoever it reached would be standing *inside* the masking boundary. Direct invitations are addressed by **id** (`/v1/groups/invitations/:id…`), authorized against `invited_user_id`, and a non-target gets **404, not 403** — the same rule as `requireMembership`, where an outsider can't learn a group exists. `loadLiveInvite` is `kind = 'link'` only; `loadLiveInvitation` is the direct one. Both accepts run through one private `runJoin`.
- **Creating an invitation is an upsert, and that is load-bearing.** The partial unique index `group_invites_group_invited_user_uq` cannot mention `expires_at` (not immutable, so Postgres won't index it), so an *expired but unrevoked* row is not live to `inviteRejection` yet still occupies the index. A check-then-insert would 23505 forever and that person could never be re-invited to that group. `LIVE_INVITATION_PREDICATE` must stay identical to the index predicate or the ON CONFLICT arbiter silently stops matching. Resend is the same call — there is no second route.
- **`declined_at` is not `revoked_at`.** Revoked is the sender withdrawing; declined is the recipient saying no. Collapsing them tells the sender the wrong story about their own invitation. `inviteRejection` orders `declined` above `expired` so a declined invitation never later reports as "expired", and `inviteRejectionMessage` is kind-aware because a used `maxUses: 1` row means "you already joined", not "exhausted".
- **The sent list shows the email string and nothing else** — no name, no avatar, not even after acceptance. The 404 on an unknown address already reveals whether an email is registered (a deliberate call); joining `users` for identity would upgrade that into `email → display name + photo` for anyone who can create a group alone.
- **Seat caps are checked at invite time as well as accept time**, counting live invitations as occupied. The accept-time check is the authoritative one, but without the advisory one the invitee gets notified, taps Accept, and only then learns the group was full.
- **`group_members.status = 'invited'` stays unused.** It sits inside `group_members_group_user_current_uq`, so writing one makes the invitee's own later accept hit 23505 and get reported as "Already a member of this group" — a confidently wrong error for the one person entitled to join.
- **The inbox is the one Groups payload with no masking**, because it holds only a group name, its size, and the sender's name — all disclosed by the sender in the act of inviting. That is a reason it needs none, not licence to add a field that would.

**On the mobile side**, Accept never joins from a card: it routes to [join-group.tsx](apps/mobile/src/app/join-group.tsx) with `?invitationId=`, which normalizes both invite shapes into one consent screen so a personal invitation and a pasted link can't drift apart. `invitations` is deliberately **excluded from the store's `partialize`** (it names other people, and a stale copy would show an invitation since withdrawn) and **is in `reset()`**, or it outlives a sign-out. The Groups tab counts an invitation as content — otherwise someone invited to their first group lands on the empty state, which *replaces* the list, and the invitation they were notified about is nowhere on screen. The tab badge is `hidden` at zero, never the string `"0"`.

Still open: the shared link remains dead text — `mtbz.app` is unclaimed, so there is no `associatedDomains`/`intentFilters`/`+native-intent.ts` and a recipient must paste it. Direct invitations sidestep that entirely (they resolve in-app), which is why claiming the domain is a named gap rather than a blocker. Inviting an address with no account is refused outright; reaching those people needs the mail send, which does not exist yet.

## Join requests

The inverse of an invitation: authored by the joiner, decided by the group. `group_join_requests` is its own table because none of that fits `group_invites` — different author, inverted authorization, its own lifecycle. Reachable **only** through a link created with `requiresApproval`, which is a link-only flag: a person-to-person invitation is already a decision about that person, and `group_invites_direct_check` refuses the combination in the database.

- **`share_config` on a pending request is the codebase's only consent snapshot**, and CLAUDE.md otherwise says there are none. It can't be avoided: there is no membership yet to read a live config from, and the consent screen's promise is that nothing is joined before the toggles have been seen. It is a *proposal* — it governs nothing until approval merges it onto the category defaults, after which the live membership config is the only thing masking ever consults. The schema comment says so; don't "tidy" it into a general pattern.
- **The approver sees the resolved config, not the stored patch.** `listJoinRequests` merges `shareDefaultsFor(category, 'member')` with the snapshot using the *same* expression `approveJoinRequest` applies. Normalizing the raw partial instead reads as "shares nothing" for someone who switched one toggle off — the wrong answer to the only question that screen asks.
- **`acceptInvite` 409s on an approval-gated token.** `previewInvite` returns `requiresApproval` so the consent screen offers Request instead of Join, but a client that skipped the screen must not walk straight past the group's approval. The reverse is guarded too: requesting on an open link 409s.
- **`pendingRequestCount` is 0 for anyone who can't act on it.** It only counts for owners, admins and trainer-group coaches — a badge a plain member can't do anything about is noise, and the count is what feeds the Groups tab badge alongside invitations.
- **Approving re-checks the seat cap inside the transaction**, and the request row is locked `FOR UPDATE` so two admins approving at once can't both insert a membership.
- **Declining sends no notification.** A silent no is kinder than a ping; approval does notify. Cancelling is scoped to the request's author, which is what makes the `cancelled` status something a user reaches rather than a decorative enum value.

Route note: `groups/requests/:requestId/cancel` has a static second segment so it can never shadow `groups/:id/requests`.

## Push notifications

[apps/api/src/notifications/](apps/api/src/notifications/) owns the push stack, and will host the mail seam when it lands. It is imported *by* `GroupsModule` and imports nothing back, so a domain module can notify without this one collecting a dependency on every feature that wants to. `device_push_tokens` is unique on the **token**, not on `(user, token)`: a device belongs to whoever is signed in on it *now*, so re-registering reassigns the row rather than adding one.

- **A push body may contain only a group name and a person's display name.** Never a number, never a nutrition field, never anything gated by a share config. A notification is assembled outside the service layer, never passes through [masking.ts](apps/api/src/groups/masking.ts), lands on a lock screen, and is never re-checked — masking has no reach here, so the bound is stated on `PushPayload` and has to be kept by hand.
- **Send after the transaction commits, and don't await it.** Inside the transaction a rollback (a unique race, a seat cap) would still have fired the push, telling someone about an invitation that doesn't exist. Awaited, a slow Expo request would turn a successful write into an error the sender sees. `sendToUser` never throws.
- **`DeviceNotRegistered` must prune the token.** Tickets come back in request order, which is how a dead token is identified. Skip this and the table only grows — an uninstalled app leaves a token that fails forever and every later send pays for it. This is the whole reason `expo-server-sdk` is a dependency rather than a `fetch`.
- **The token handback runs before `signOut`.** [lib/session](apps/mobile/src/lib/session/index.ts) `endSession` is three steps now: unregister, sign out, wipe. The unregister call is authenticated and `signOut` drops the cookie it needs, so reversing them leaves this device bound server-side to the account being left — and the next person to sign in here gets the previous account's notifications. Best-effort, like everything else there: an offline user must still get out.
- **Order on the client is channel → permission → token.** On Android 13+ the OS prompt doesn't appear until a channel exists, and a channel is a prerequisite for a token at all. `setNotificationHandler` sits at module scope in [lib/push](apps/mobile/src/lib/push/index.ts), and returns `shouldShowBanner`/`shouldShowList` — **`shouldShowAlert` is deprecated in SDK 57 and silently shows nothing**. iOS permission is read off `settings.ios.status`, not the root `status`, which collapses `PROVISIONAL`. `projectId` is passed explicitly to `getExpoPushTokenAsync`; the implicit fallback is what breaks in standalone builds.
- **The prompt is asked for on the Groups tab**, not at launch — it is the only surface that sends anything, and the OS offers the prompt once. Sign-in re-registers with `promptIfNeeded: false` so a second device that already said yes works without visiting the tab.
- **A tap has two sources.** `getLastNotificationResponseAsync` for a tap that launched the app cold (already happened before any listener could attach) and `addNotificationResponseReceivedListener` for everything after. Both are guarded on `onboardingComplete`, since `/invitations` lives inside `Stack.Protected`.

Everything degrades to "no notification" rather than an error: no permission, a simulator, an unconfigured build, an unreachable API. Credentials (FCM v1 + `google-services.json`, APNs `.p8`) are in [DEPLOYMENT.md §3b](docs/DEPLOYMENT.md) and are **not** blocking — without them invitations still arrive, they just wait in the inbox instead of announcing themselves.

## Catalog review

Users create foods ([create-food.tsx](apps/mobile/src/app/create-food.tsx) → [create-food-screen.tsx](apps/mobile/src/components/log/create-food-screen.tsx), reached from the "Can't find it?" row at the bottom of search **including the no-results state**). A `public` one is **live in everyone's search immediately** and is reviewed afterwards.

**There is deliberately no `pending_foods` staging table.** `diary_entries.food_id` has to FK somewhere and search would otherwise UNION two identical shapes, so a live-but-unreviewed food is a *state*: `foods.review_status` (`pending | approved | rejected | needs_edit`), plus two append-only side tables (`food_reviews` — decisions; `food_reports` — user "this looks wrong"). The queue index is partial (`pending AND public AND owner_id IS NOT NULL AND deleted_at IS NULL`) so it stays proportional to the queue, not the catalog.

Rules that fall out of that:
- **`isVerified` is derived, never stored.** The old `foods.is_verified` column is gone (migrations `0008`/`0009` — `0008` backfills *while the column still exists*, `0009` drops it). Every read is `reviewStatus === 'approved'`; the DTO keeps `isVerified` as a convenience field so the mobile contract didn't churn. Never reintroduce a second source of truth for this.
- **`review_status`, `review_flags`, `reviewed_by/at/version` are server-controlled** and are absent from `createFoodSchema`/`updateFoodFieldsSchema` on purpose. A client that could set its own status makes the queue decorative.
- **Editing nutrition on an approved food re-queues it** to `pending` (`CatalogService.updateFood`) and appends a `food_reviews` row. Without this, approval is a laundering step: publish something honest, get the badge, rewrite the macros underneath it. Non-nutrition edits (name, description) do not re-queue.
- **`rejected` is excluded from search entirely** — including from its own owner's — but stays readable by id, so reopening a diary entry that referenced one still works. `needs_edit` stays public and ranks with `pending`.
- **`diary_entries.verified` is derived server-side** at log time from the food's status, not taken from the request body — it is a claim the *catalog* makes, so a client must not assert it about a food it invented seconds ago. It is a snapshot and goes stale by design, exactly like the macros on the same row.
- Search ranks `own → prefix → approved → popularity → name → id`. The keyset cursor's `ver` component means "approved" and is selected with `.as()` so Postgres and JS can never disagree on it.

[evaluateFoodFlags](packages/shared/src/food-review.ts) is where the feature's value lives — it turns "an admin reads thousands of rows" into "an admin triages a handful". Pure and dependency-free, so **the same function runs on the create-food form as the user types** (warn, never block) and on the server at write time. Two codes need a database and are appended by the API instead: `duplicate_name_brand`, and `first_record_for_gtin` (Phase 2). `energy_unit_confusion` is evaluated first and **suppresses `atwater_mismatch`**, because a kJ figure typed into a kcal field always fails both and the pair buries the one that says what happened.

**On the admin side** ([review.ts](apps/admin/server/review.ts), the SPA's third tab): these are the **only** routes in that tool that *edit* user rows (sync copies them, verbatim — see below). `systemFood()` in [foods.ts](apps/admin/server/foods.ts) still guards every system-catalog route and **must not be loosened** — review has its own `userFood()` filter and the two never meet. The queue orders **barcode-bearing rows first**, then severity, then FIFO: a barcode is a global key, so one bad record is served to everyone who ever scans that product. `ADMIN_REVIEWER_ID` is a **stopgap for attribution only** — the tool has no auth and authorizes nothing.

**On the mobile side**, absence is again a designed state, not a blank: an unapproved public food someone else added renders an explicit "Unverified" chip rather than a missing badge, the same promise the groups UI and the day-states make. The kJ/kcal toggle on the energy field defaults to **kJ** because AU/NZ panels are kilojoule-primary — a kJ figure entered as kcal is 4.184× too dense and lands inside the plausible range, exactly like the weight sheet's kg/lb problem. Energy is converted **once, at the input boundary**, and only kcal is ever stored.

## Live → local sync (admin tool)

Pulling a live test account onto a laptop, so a bug report about a real user's diary can be reproduced. The SPA's fourth tab; [sync.ts](apps/admin/server/sync.ts) is the guard rail and HTTP shape, [sync-plan.ts](apps/admin/server/sync-plan.ts) the engine (an ordered `SPECS` list of tables + a generic collect → diff → write). `SOURCE_DATABASE_URL` (optional, live) is the source; `DATABASE_URL` is the only thing written. Runbook: [DEVELOPMENT.md §6](docs/DEVELOPMENT.md).

- **One direction, enforced three ways.** Every live read runs in a `read only`, `repeatable read` transaction; nothing opens a write path to the source; and sync **refuses to run unless `DATABASE_URL` is a loopback host — with no override**, because the failure it prevents is a `.env` with the two URLs swapped pushing local test data into production. It also refuses when both name the same database.
- **Preview and apply are one code path** (`runSync(..., { apply })`), and preview opens the local transaction `read only` — so a bug cannot make a preview write. Apply re-collects rather than trusting a plan the client sends back.
- **`accounts` is copied; `sessions`, `verifications` and `device_push_tokens` are not.** Without the credential row the synced user cannot sign in, which is the entire point. A copied push token would mean a local dev send firing at a real phone — the one row here that could reach outside the laptop.
- **`source_ref` is a natural key; barcode deliberately is not.** Each database ran the USDA import separately, so the same food carries two UUIDs and inserting live's trips `foods_source_ref_active_uq` forever. A natural-key match makes the incoming row adopt the **local** id and rewrites the FKs pointing at it (`remap`), dropping the duplicate's portions. A shared *barcode*, by contrast, may be two genuinely different records, so it raises a **blocker** instead — as does an email already held locally under a different id. Blockers refuse the apply; guessing either way loses information only a human has.
- **Prune runs before insert**, not after: a local-only row occupying a partial unique index (an `active` `group_members` row for a pair live also has) is exactly what would 23505 the insert meant to replace it. Prune is opt-in and scoped to the selected users' **own** rows — never another member's, never a `groups` or `users` row (both cascade far outside the sync), never the system catalog.
- **A `groupScoped` spec is skipped entirely when `includeGroups` is off.** Not cosmetic: the scope context includes groups discovered on the *local* side, so leaving those specs running against an empty snapshot reports every local group row as local-only, and prune would then delete the memberships of the feature the operator just excluded.
- Foods the selected users merely *reference* are `insertOnly` — pulled to satisfy `diary_entries.food_id`, never updated, so a local admin correction to a system row survives a sync.
- The report is per column, not per table: `changedColumns` plus `before → after` samples. "22 new, 3 changed" with no idea *what* changed is the version of this feature that gets used once and then distrusted.

## Regions, units and carbohydrate

Metabolizm's users are in **NZ/AU**; the seeded catalog is **USDA**. That is a correctness problem, not just a coverage one, and these four invariants are what hold it together. Each is silent-and-plausible when broken — a wrong number that looks entirely reasonable in a list.

- **`foods.carbs_g` is always AVAILABLE carbohydrate — fibre EXCLUDED.** AU/NZ nutrition information panels report available carbohydrate with fibre listed separately; US labels and USDA report *total*, fibre included. Fibre lives in `nutrients.fiber`. USDA is converted once at the **import boundary** (`1005 − 1079` in [usda-mapper.ts](apps/admin/server/usda-mapper.ts)), never at read time. Where the source has no fibre value the conversion is impossible, so the row keeps the total and is stamped `carbs_include_fibre` rather than guessed at. Migration `0011` converted the already-imported rows — **a data migration, not a script, because subtracting fibre is not idempotent** and nothing on the row distinguishes converted from unconverted.
- **Energy is always stored kcal.** AU/NZ panels are kJ-primary and often omit kcal entirely, so the create-food form has a kJ/kcal toggle defaulting to **kJ** for NZ/AU users, converting once at the input boundary (`kcal = kJ / 4.184`). A kJ figure typed into a kcal field is 4.184× too dense and lands inside the plausible range — no server bound catches it, which is why `energy_unit_confusion` exists and why the toggle must stay visually unmissable. Exactly the weight sheet's kg/lb problem.
- **Barcodes are always stored GTIN-14**, zero-left-padded ([gtin.ts](packages/shared/src/gtin.ts)). UPC-A (12), EAN-13, EAN-8 and ITF-14 collapse to one comparable form; storing them as scanned is what makes a US product entered as 12 digits invisible to a 13-digit lookup of the same product. `normalizeGtin` also detects GS1 **restricted-circulation** prefixes (store weight/price labels), which can never resolve against any database — `GET /v1/catalog/foods/by-barcode/:code` answers **422** for those, distinct from a 404, because a user told "not found" just rescans the same label forever. The barcode unique index is **partial on public rows only**: a private food may carry any barcode, and the old catalog-wide index wrongly 409'd a food only its owner could see.
- **`users.region` ranks, it never filters.** Same one-writer rule as `users.timezone` (the `users` module) and the same trap — the `'NZ'` default is a fallback, not an answer, so onboarding pushes the device locale explicitly (`pushDeviceRegion`, beside `pushDeviceTimezone`). `regionRank` sits between prefix match and approved: exact market 2, same market group **or unknown** 1, elsewhere 0. **AU and NZ are one group** (Trans-Tasman brand overlap), and empty `markets` scores neutral rather than as a mismatch — most of the catalog is unknown, and penalising that would bury the entire USDA import for every NZ user. A New Zealander who bought an American protein powder must still find it, just lower; hard filtering turns a ranking problem into "your app doesn't have my food". The supported list lives in [regions.ts](packages/shared/src/regions.ts) so api and mobile cannot drift.

Barcode coverage in every open database is thin here (Open Food Facts holds ~15k NZ products), so **scan → not found → add it is a primary flow**, not an edge case. That is why the not-found state is framed as a contribution rather than a failure, and why the review queue is load-bearing.

**Open Food Facts attribution — unresolved, deliberately.** Anything cached from OFF must carry `source_ref` prefixed `off:<gtin>`. The OFF *database* is ODbL, whose share-alike obligations reach derived databases, and whether a commercial catalog embedding OFF rows triggers them is a real legal question that is **not settled in code**. The provenance prefix is in place so we can honour it and re-sync later rather than silently forking their data; the licensing call is still open.

## Architecture

All paths below are inside `apps/mobile/`. Routing is file-based via expo-router (`main: "expo-router/entry"`). [src/app/_layout.tsx](apps/mobile/src/app/_layout.tsx) is the root layout: it loads the Space Grotesk / Instrument Sans fonts (`useFonts`, gating render on load), sets up the ThemeProvider and splash overlay, and gates first-run via a Stack — the `(onboarding)` group until `onboardingComplete`, then the `(tabs)` group plus the `add-food` / `food-detail` full-screen modals, `day-picker` (the calendar, a native `formSheet`), the Groups drill-downs (`group/[id]`, `member-day`, `create-group`, `join-group`, and `group-sharing` as a modal), and `profile`. Those push at the ROOT stack, above the tab group, so they carry their own [screen-header.tsx](apps/mobile/src/components/ui/screen-header.tsx) rather than the tabs' persistent `AppHeader`. `create-group`/`join-group` are deliberately pushes, not modals: each `replace`s itself with the group it produced, which would otherwise strand the group detail in a modal presentation.

Tab routes live in [src/app/(tabs)/](apps/mobile/src/app/(tabs)/): `index.tsx` (**Log — the landing tab**; it owns the index route because native tabs always open on `index.tsx` and there is no initial-tab override), `vitals.tsx` (the stat-tile grid — **only tiles with a real data source ship**: weight, plus protein and energy from today's diary. Steps/sleep/heart need Apple Health or Health Connect and water/fasting need their own log paths; rendering those with sample numbers would break the same promise the groups UI makes. Older draft cards remain unreferenced in [src/components/dashboard/](apps/mobile/src/components/dashboard/) — note `weight-card.tsx` there is superseded and fabricates its series from `sample-data.ts`, so don't wire it up), `groups.tsx`, and `recipes.tsx`. The group's [_layout.tsx](apps/mobile/src/app/(tabs)/_layout.tsx) renders the shared [app-header.tsx](apps/mobile/src/components/app-header.tsx) (plan icon · date · profile button) above the tabs — persistent across all tabs because native tabs don't provide a header.

**Profile & settings is not a tab.** [src/app/profile/index.tsx](apps/mobile/src/app/profile/index.tsx) pushes at the root stack from the `AppHeader`'s profile button, which is its only entry point (each setting is its own screen under `profile/` — `targets`, `goal`, `units`, `appearance` — so the index stays a scannable list of rows) — the tab bar is reserved for the surfaces opened daily, and profile is the app's lowest-frequency destination. Anything set-once (theme, notification preferences, data export) belongs behind that button too, not in the tab bar.

**Platform-split components** are a starter pattern: files with a `.web.tsx`/`.web.ts` suffix replace their native counterpart on web. Web is not a shipping target (see Project), so the `.web.*` files are effectively legacy — but keep them in sync if you touch the native side, since they still get bundled.

- [app-tabs.tsx](apps/mobile/src/components/app-tabs.tsx) uses `NativeTabs` from `expo-router/unstable-native-tabs` (native tab bar), while [app-tabs.web.tsx](apps/mobile/src/components/app-tabs.web.tsx) builds a custom floating header from the headless `expo-router/ui` Tabs primitives. **A new tab route must be registered in both files.**
- Same pattern for [animated-icon.tsx](apps/mobile/src/components/animated-icon.tsx)/[animated-icon.web.tsx](apps/mobile/src/components/animated-icon.web.tsx) (splash overlay) and [use-color-scheme.ts](apps/mobile/src/hooks/use-color-scheme.ts)/[use-color-scheme.web.ts](apps/mobile/src/hooks/use-color-scheme.web.ts).

**Theming — the "Kinetic" design system** lives in [src/theme/](apps/mobile/src/theme/): `palette.ts` (light/dark `ThemeColors` incl. role aliases `actionPrimary`/`inkStrong` and precomputed `*Soft` alphas), `typography.ts` (`Fonts` + the `Type` scale — Space Grotesk for display/ALL numerals with `tabular-nums`, Instrument Sans for UI/body), `tokens.ts` (`Spacing` 4px grid, `Radius`, `Motion`, `Elevation`), and `provider.tsx` (context `ThemeProvider` + `useTheme()` → `{ scheme, colors }`; also feeds the expo-router nav theme). The scheme resolves from `preference.ts` — a `system`/`light`/`dark` choice persisted through **MMKV specifically because it is synchronous**, so the first paint already has the right scheme instead of flashing light. `system` is stored as the choice itself, never as the scheme it currently resolves to, or "System" would freeze at whatever the OS was when it was picked. It is a **device** preference, not account data: it lives in `src/theme/`, not `src/store/`, and `clearLocalData` must never reset it — signing out or deleting the account leaves the phone looking how its owner set it. Never hardcode colors in screens — consume via `const { colors } = useTheme()`, `ThemedText`/`ThemedView`, or the kit in [src/components/ui/](apps/mobile/src/components/ui/) (Button, IconButton, Input, StatNumber, Badge, MacroBar, Card). **Role rules**: `accent` (lime) only for active states/progress/streaks/active tab (never body text, never lime text on light bg — use `accentText`); `macro*` colors only on macro visuals; `success`/`danger` only for status; selected/focused = 2px `focusRing` border. The provider's context values are frozen module constants — don't rebuild them per render (reactCompiler is on).

**Weight & the chart.** The weight vertical lives in [src/components/vitals/](apps/mobile/src/components/vitals/), the `weight/index` and `weight/history` root-stack routes, and [store/weight.ts](apps/mobile/src/store/weight.ts) (zustand + MMKV, generous cache — weight data is tiny and the tile must paint before any network call). [weight-chart.tsx](apps/mobile/src/components/vitals/weight-chart.tsx) is drawn with **react-native-svg**, chosen over Skia/victory-native because those add 4–6 MB to the download for one screen. Its gestures need the `GestureHandlerRootView` in the root layout — without it the scrub silently never fires on Android. The chart builds its own path and domain; the crosshair rides a Reanimated shared value on the UI thread and React only hears about a *change of selected point*, which is also what makes the haptic land once per data point. Do not move the gesture construction into `useMemo`: reactCompiler treats a `useMemo` body as render code and rejects shared-value writes inside it.

**The day switcher.** The Log tab shows any day: history back through the retained window, and up to **`DIARY_MAX_FUTURE_DAYS` (30) days ahead** for planning. A planned day is an ordinary `diary_entries` row with a future `entry_date` — there is no separate "planned" concept, so when the day arrives the plan simply *is* the log. [loggableEntryDateSchema](packages/shared/src/diary-schemas.ts) bounds writes (UTC today + 32, absorbing the timezone spread) because one entry dated 2099 would sit at the top of every `max(entry_date)` read forever; **reads stay unbounded** — a history query legitimately spans years.

The week strip ([day-strip.tsx](apps/mobile/src/components/log/day-strip.tsx)) lives on the Log tab, **not** in `AppHeader`, which renders above all five tabs where a selected day means nothing. The header keeps the streak pill, the date, and the way into the calendar ([day-picker.tsx](apps/mobile/src/app/day-picker.tsx), a root-stack `formSheet` — the OS owns the drag/detents/dismiss, so no bottom-sheet library is in the bundle). The calendar grid, the rings ([progress-ring.tsx](apps/mobile/src/components/ui/progress-ring.tsx), react-native-svg) and all date math ([lib/dates](apps/mobile/src/lib/dates/index.ts)) are hand-rolled: **no calendar or date library**, for the same size reasons as the weight chart, and because a date lib re-introduces exactly the local-`Date` DST bug class that `YYYY-MM-DD` string math avoids.

**Nothing about this is on the launch path.** The strip sums diary entries already in MMKV, so a cold start issues no request at all. `GET /v1/summaries/days` ([SummariesController](apps/api/src/summaries/summaries.controller.ts), ≤400 days — far wider than the diary's 31, because a summary row is ~120 bytes) is a **browse-time gap-filler** for days the device no longer holds, fetched when the calendar sheet opens. The rule between the two caches is one-directional and there is no merge: `daily_summaries` is a *projection* of diary entries, not an independent record, so **local entries win for every day they cover** and a summary is consulted only for days outside the window ([use-day-states.ts](apps/mobile/src/hooks/use-day-states.ts)). The one field that inverts is the **target** — a summary carries the target in force *for that day*, so a past day scores against its snapshot rather than today's goal.

Three invariants that keep the UI honest:
- **Absence is not zero.** `unknown` (not loaded) is distinct from `unlogged` (the day ended empty), which is distinct from a logged 0 — see [day-status.ts](apps/mobile/src/lib/diary/day-status.ts). `lastFullSync` on the diary store is what licenses reading an absent in-window day as empty; before it lands the cell renders a skeleton. Same promise the groups UI makes by never rendering a withheld value as a blank.
- **The streak is derived locally** (`localStreak`), so it is instant, offline, and never stale. The server's count is fetched *only* when the local run reaches the edge of the 90-day window and the real streak is longer — for most accounts, never. Future planned days can never inflate it; the walk goes backwards from today. Thresholds (`CALORIE_BAND` etc.) live in [packages/shared/src/summaries.ts](packages/shared/src/summaries.ts) so the client colours a day exactly as the server's group adherence scores it.
- **`pruneDays` is anchored on today** (`today−90 … today+31`, plus the day being viewed), never "the N latest keys". Once a day can be planned ahead, the future days are the chronologically largest and a `slice(-N)` evicts today and all history.

`checkDayRollover` follows midnight — via AppState for an app resumed the next morning, via Log tab focus for one left open overnight — and only moves the selection when the user was actually sitting on the old today.

**Units.** Every weight crossing the API is in kilograms; `unit` on a response is a display preference. Convert once at render via [lib/weight](apps/mobile/src/lib/weight/index.ts), never per point and never server-side — rounding in both places drifts the chart away from the history list. The server's 20–500 kg bound cannot catch a pound value typed as kilograms in the normal human range (165 lb entered as kg is a plausible 165 kg and is accepted), so the unit toggle in the log sheet has to stay visually unmissable.

**Path aliases** ([apps/mobile/tsconfig.json](apps/mobile/tsconfig.json), app-internal): `@/*` → `src/*`, `@/assets/*` → `assets/*`. Shared data shapes (catalog/food, health, diary, profile types) are imported from `@metabolizm/shared` — the app barrels (`@/lib/api`, `@/lib/food`, `@/lib/health`) export runtime helpers only, not types.
